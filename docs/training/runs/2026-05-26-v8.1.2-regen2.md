# v8.1.2-regen2 SFT training run — 2026-05-26

## Why this run exists

The rehydration-kernel/main copy of `prepare_operator_sft_dataset.py`
reports `by_action: unknown` on v8.1.2-v6 trajectories — it does not
understand the current operator action DTO schema. The operator-repo
copy of the same script handles the schema correctly.

If the buggy script affected only the coverage report, v8.1.2-sft-v2
weights are fine and this run will produce an equivalent model. If the
buggy script also affected actual training rows (mis-labeled actions,
wrong arguments, dropped rows), v8.1.2-sft-v2 weights may be flawed and
this run will outperform the baseline.

This is a **diagnostic run**, not an expected improvement. Honest prior:
~50/50 the regen yields no measurable delta.

## What this run will NOT improve

- Live MCP success rate against the v8.1.2 eval split. Synthetic refs
  remain absent from production KMP — separate Path 2 issue.
- Read-profile action_match on holdout. Baseline already at 222/222
  (1.000) on the regen2 eval split (verified Gate 4.7 holdout-direct,
  16/16 sample).

## What this run MIGHT improve

- Write-profile action_match. Baseline 0/19 kernel_ingest + 1/22
  kernel_write_memory. Regen2 has 320 + 320 properly-formatted write
  rows; if buggy labels were the cause of the write gap, cleaner labels
  may move this needle.
- Contract validity uniformity. Baseline 100% on read, ~95% on write;
  small upside possible.

## Decision criteria

Compare regen2 adapter against v8.1.2-sft-v2 on the same eval split:

- **Regen2 ≥ baseline + 2pp write-profile action_match**: candidate for
  v8.1.3 deploy. Open separate PR to swap adapter in env/prod operator
  values, document the delta in model-history.md.
- **Regen2 ≈ baseline (±1pp)**: keep v8.1.2-sft-v2 deployed. Document
  the regen exercise as confirmation that the buggy kernel script was
  cosmetic (coverage report only, not training rows). Archive the regen2
  adapter at `/tmp/operator-qwen05-lora-v8.1.2-regen2-<UTC>/` for
  reference.
- **Regen2 < baseline**: STOP and analyze. Do not deploy. Investigate
  what regression appeared (LoRA seed? Data ordering? Truncation
  differences?).

## Risks + mitigations

- **GPU contention**: if other jobs are running on the 4×3090, this job
  will queue. Verify GPU availability before launch.
- **Disk space**: previous training artifacts in /tmp may eat space.
  Verify > 20 GB free before launch.
- **K8s job failure mode**: if pod crashes mid-training, the loss
  trajectory is lost. Background log observer mitigates by capturing
  per-step output as it happens.
