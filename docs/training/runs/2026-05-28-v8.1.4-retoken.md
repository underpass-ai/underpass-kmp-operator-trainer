### Failure-bucket interpretation

- The 9 failures eliminated were genuine generation-budget truncation. The only `incomplete_json` left in Run B is internal brace imbalance (`raw_len` 5582 chars, well under any budget), not truncation.
- `missing_action_kind` rose 1 → 3. These predictions ended with the wrong number of closing braces, omitting `"kind":"tool_call","tool":"kernel_ingest"` before closing the action object. Not budget-related. Likely stochastic given the small absolute count.
- `invalid_json` (2) and `relations[0]_not_object` (1) are unchanged. Both are structured-output grammar drift that 4096 cannot fix.

## Findings

1. Run A (2048) was under-evaluating `kernel_ingest`: 7 of its 14 failures were length-truncation. Run B (4096) recovers 7 predictions, of which 6 are exact matches.
2. The recovery is confined to `kernel_ingest`. No other tool changed. Conditional accuracy on parsed outputs is essentially flat (91.75% → 91.61%, within noise).
3. v8.1.4's structural deficit is `kernel_ask` (12 / 32 exact = 37.5%). That regression is independent of `max_new_tokens`. v8.1.3pa scored 17 / 32 exact on `kernel_ask`. The corpus or training change between v8.1.3pa and v8.1.4 hurt the `kernel_ask.query` inference path, which is what the v8.1.4 audit already identified.
4. Schema/grammar drift on `kernel_ingest` (the 4 missing_action_kind / invalid_json / relations[0] failures in Run B) is unrelated to token budget. These are model errors in producing well-formed JSON near the end of large nested payloads.

## Decision

- Do not ship v8.1.4, including the retoken evaluation. The corrected predict still leaves v8.1.4 below v8.1.3pa on the metric that matters (`kernel_ask` exact-match, and conservative exact overall when accounting for the different eval mix).
- Keep v8.1.3pa as the deployed candidate. Currently installed at `/var/lib/operator-adapters/v8.1.3pa-candidate/` with SHA `3953786b7b18163c1e6e72b08acf5a33631f2ef6a8bb2de79c1f1fe724829156`. Helm revision 3 was last to mount it; deployment is presently scaled to 0.
- Do not install v8.1.4 under `/var/lib/operator-adapters/`. Do not load v8.1.4 into the vLLM endpoint.

## Follow-ups (proposed)

1. Parameterize predict `max_new_tokens` in the manifest. The current `k8s/qwen05-lora-predict.yaml` hard-codes `--max-new-tokens 2048` inline. For long-payload evals (`kernel_ingest`-heavy) 4096 should be selectable without editing repo YAML. (Addressed in same PR as this doc.)
2. Optional offline JSON-repair analysis. The 7 surviving v8.1.4 failures and any new ones from future runs are structurally close to valid (extra `]])`, `}}}}` instead of `}}`, `[[]]` instead of `[]`, missing trailing `"kind"`/`"tool"`). An offline pass that records `repair_applied: true/false`, the repair delta, and post-repair contract validity would let us measure "model-output is fixable" vs "model-output is wrong" without changing training. This is analysis, not a runtime auto-repair: silent rescues must not inflate live metrics.
3. v8.1.5 ask-only prepared_action experiment. The "narrowest defensible next experiment" remained: keep `AskArguments` unchanged, inject top-level `prepared_action` for `kernel_ask` only in SFT rows, train as a controlled v8.1.5 experiment, compare `kernel_ask` exact-match against v8.1.3pa, and verify no read/write regressions. (See `runs/2026-05-28-v8.1.5-ask-pa.md`.)
